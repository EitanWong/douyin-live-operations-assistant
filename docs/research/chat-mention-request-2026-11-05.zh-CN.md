# 直播普通弹幕的真实 @ 请求

## 实播观察

2026-11-05，在用户指定的 `live.douyin.com/260440030123` 直播间，通过在线观众“懒二🐑”的资料卡 `.mention` 按钮插入原生 @，追加“ @功能测试，打扰啦”并发送。输入框出现不可编辑的 `.atBlock`，带 `data-at-uid` 和 `data-at-name`；这与直接键入昵称不同。

Chrome Network 实见 `GET /webcast/room/chat/`，HTTP 200，响应 `status_code: 0`，公屏出现带 @ 的本人消息。仅保留与协议有关的字段；不保存或复用 Cookie、msToken、a_bogus 等会话与签名值。

```js
{
  room_id: '<当前房间字符串ID>',
  content: '@懒二🐑  @功能测试，打扰啦',
  type: 0,
  rtf_content: JSON.stringify([{
    type: 2,
    value: JSON.stringify({uid: '<目标观众字符串UID>', webcast_uid: ''}),
    start: 0,
    length: 5
  }]),
  paste_edit_method: 'non_paste'
}
```

`length: 5` 覆盖 `@懒二🐑`：@ 占 1、两字占 2、🐑 占两个 UTF-16 code units。`start` 和 `length` 是 JavaScript 字符串偏移，不能用 `[...text].length` 计算。`value` 本身是 JSON 字符串，整个 `rtf_content` 再序列化一次；不是 `at_user_id`，也不是简单的 `@昵称`。

本次网络证据通过 Chrome DevTools 的原生界面读取。当前 Chrome 没有暴露 loopback CDP 端口，因此没有 REA Evidence ID，不将技能使用或静态推断冒充 REA 运行捕获。受限于本人页面观察，未独立确认被 @ 者设备收到提醒。

## 项目发送契约

引擎在最终消息清理、合并完成后解析完整 @ 昵称，产生 `{id,start,length}[]`。仅使用本房已观察、未过期且昵称唯一的字符串 UID；不把 secUid、昵称前缀、邮箱或同名观众猜成目标。查询提示、完成答复及刷新中断反馈保留任务绑定的 UID，允许现有字数预算使用截短显示名。昵称清理与最终发送正文复用同一个规范化函数。

适配器、隔离桥与 MAIN 全程携带这些片段，MAIN 在调用原生 HTTP client 之前验证 UID、范围、顺序和表情边界，然后构造上述 `rtf_content`。复用网页现有 client 的会话、签名拦截器和响应处理，不复制签名。成功后使用原有本地公屏队列，保留服务端 `rtf_content_v2`。

真实 @ 使用本次验证过的普通聊天通道；原任务要求管理员弹幕时转普通弹幕并报告原因。普通聊天请求能力不可用时保留任务等待恢复，不退化到编辑器发送一个无身份的假 @。未知提交结果沿用不自动重发规则，同一票据只提交一次。

没有可靠身份的文本不会凭空产生结构化 @；它仍是原有正文。没有修改普通回复的称呼风格，也没有给所有消息强加 @。管理员接口的富文本协议、其他接收端的通知行为及平台未来协议变化均未由本次观察证明。
