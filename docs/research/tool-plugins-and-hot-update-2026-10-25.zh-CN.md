# 扩展工具插件化、热更新与 Cordis 评估

调研日期：2026-10-25。范围：当前仓库的 Chrome Manifest V3 扩展、Tampermonkey 兼容产物，以及 Cordis 当前发布包与官方源码。本轮完成架构评估和临时目录中的独立实验，未改动业务代码或项目依赖。

后续实施更新（2026-10-26）：统一接口及自动点赞、福袋红包试点已完成，随后按用户要求通过运行时适配层接入 `cordis@4.0.0-rc.12` 核心。下文保留调研时的评估结论；当前实现及边界见[包内工具插件开发](../development/tool-plugins.zh-CN.md)。

## 推荐决策

**值得将“扩展工具”做成插件架构。现阶段先建立小范围的工具宿主和稳定接口；Cordis 核心作为候选适配层，暂不引入整套加载器、HMR 或插件市场。**

优先目标是：新增工具通过注册接入；单个工具可独立启停、回收资源和报告故障；工具失败不会阻塞礼物记账、直播事件采集与主发送队列。插件化本身不等于浏览器进程隔离，也不提供跨崩溃的数据恢复保证。

在当前只有“自动点赞”一个独立扩展工具、主业务已有持久日志和恢复机制的情况下，直接改造整个应用的风险高于收益。先用自动点赞验证接口，并让下一个实际工具验证接口是否通用。依赖关系、服务替换和嵌套生命周期成为反复出现的需求时，再比较采用 Cordis 核心与继续维护自有宿主的成本。

## 当前代码已经具备什么

| 已确认现状 | 代码依据 | 对扩展性的影响 |
| --- | --- | --- |
| 开发监听会构建、重载扩展并刷新直播页；更新前等待页面恢复点及后台写入 | `scripts/dev.mjs`、`extension/development-reload.js` | 已有开发自动更新，但存在刷新窗口，不是直播采集无中断的 HMR |
| 保存配置后直接调用 `engine.update(c)` | `src/app.js` 的 `save` 回调 | 已有配置在线生效能力，不需要为此单独引入元框架 |
| 自动点赞在应用中直接实例化，启停回调、250 ms 检查及页面离开处理均由应用接线 | `src/app.js`、`src/core/auto-like.js` | 很适合先包装为插件，复用现有业务实现 |
| 工具菜单、页面模板、按钮事件和工具分类判断分布在 UI 文件中 | `src/ui/navigation.js`、`src/ui/panel.js` | 只增加注册器还不够；工具视图和导航也要有注册入口 |
| 已有有界收件箱、隔离队列、快照写入、检查点后日志确认与发送未知状态 | `src/runtime/inbox.js`、`journal.js`、`delivery.js` | 应复用这些可靠性边界，避免插件各自重建发送和恢复链路 |
| 主产物主要按依赖排序、去掉 ESM 导入导出后拼接；图表和部分后台模块单独用 esbuild 打包 | `scripts/build.mjs`、`scripts/build-modules.mjs` | npm 裸导入不会自动成为运行时依赖；采用 Cordis 要增加明确的打包步骤 |

尤其要保留自动点赞现有语义：停用会增加 generation、停止后续批次、等待在途请求结算；拒绝或结果未知时停止，不自动重试；刷新后由用户重新开始。资源卸载不能撤回已经提交的平台操作。

## “热更新”需要分别设计

| 能力 | 是否适合当前产品 | 推荐方式 |
| --- | --- | --- |
| 配置、话术、题库、明确字段的规则参数在线更新 | 适合 | Schema 校验、版本校验、原子替换、保留最近可用配置；执行分支预先包含在扩展包中 |
| 已打包工具的启用、停用、实例重建 | 适合，建议优先实现 | 工具宿主管理生命周期；停止新任务、处理在途状态、回收监听与计时器、重新挂载 |
| 开发环境修改源码后更新 | 已有基础能力 | 先保留现有自动构建与重载；局部 HMR 的收益需要单独验证 |
| 生产环境下载新的 JS/WASM 工具并直接执行 | 不采用为常规扩展发布路径 | 新代码随扩展包发布；不能因引入 Cordis 就绕过平台加载和审核规则 |
| 云端工具算法独立迭代 | 适合未来已有真实云端能力时 | 浏览器调用版本化服务 API，保留本地降级；本地采集、锁和平台操作仍由浏览器控制 |

Chrome 官方将远程加载后执行的 JS/WASM 归为远程托管代码；普通 JSON 数据不属于同一类别。把可执行逻辑装进 JSON、通用解释器或字符串求值并不等于数据更新。这里采用“包内代码 + 远程受限数据”的产品路线。[远程托管代码说明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)、[MV3 已知问题中的动态配置说明](https://developer.chrome.com/docs/extensions/develop/migrate/known-issues)。

当前 README 的分发方式是下载 ZIP 后加载解压扩展，不能默认获得商店自动更新；商店分发则走 Chrome 的整包更新生命周期。两种情况都不能承诺页面正在运行的业务逻辑被原地无损替换。Tampermonkey 的脚本更新也应单独处理，不作为绕过 Chrome 扩展分发约束的方案。[扩展更新生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/extensions-update-lifecycle)。

## Cordis 的实际适配情况

### 版本与边界

本次实时查询 npm registry，`cordis` 的 `latest` 为 **4.0.0-rc.12**，发布时间为 2026-10-21 UTC；`@cordisjs/plugin-hmr` 为 **1.1.2**。部分搜索快照仍指向 rc.9/rc.10，因此本评估的源码引用固定到 rc.12，未混用旧版教程。[Cordis 发布元数据](https://registry.npmjs.org/cordis)、[HMR 发布元数据](https://registry.npmjs.org/@cordisjs%2Fplugin-hmr/latest)、[rc.12 发布页](https://github.com/cordiverse/cordis/releases/tag/v4.0.0-rc.12)。

官方 README 明确说明 API 尚未稳定，官方文档仍在建设中。这是生产选型的维护成本信号，不等于框架不能使用。[固定版本 README](https://github.com/cordiverse/cordis/blob/v4.0.0-rc.12/packages/core/README.md)。

| Cordis 能力 | 对本项目的价值 | 仍需宿主完成的工作 |
| --- | --- | --- |
| 插件挂载、卸载与依赖注入 | 统一工具装配与服务依赖，减少 `app.js` 接线 | 业务权限、房间作用域、API 版本兼容 |
| `ctx.effect()` 和插件卸载 | 回收通过框架登记的资源，支持插件实例重建 | 原生监听、计时器、Observer、请求等都要通过包装登记；无法自动发现任意外部副作用 |
| 服务依赖变化后的生命周期协调 | 适合多个工具共享 AI、直播上下文和请求能力 | 持久状态、平台请求的在途语义、跨执行环境通信 |
| 官方 HMR 插件 | 可研究未来 Node 服务端的开发体验 | 依赖 Node 文件监听、路径和模块加载缓存，不能直接用于内容脚本 |
| 事件机制 | 提供组合基础 | 独立队列、容量上限、超时、熔断及逐订阅者异常处理 |

依据：[插件与卸载官方测试](https://github.com/cordiverse/cordis/blob/v4.0.0-rc.12/packages/core/tests/plugin.spec.ts)、[生命周期实现](https://github.com/cordiverse/cordis/blob/v4.0.0-rc.12/packages/core/src/fiber.ts)、[事件派发实现](https://github.com/cordiverse/cordis/blob/v4.0.0-rc.12/packages/core/src/events.ts)、[HMR 源码](https://github.com/cordiverse/cordis/blob/v4.0.0-rc.12/packages/hmr/src/index.ts)。

### 独立实验

在仓库外的临时目录安装固定版本 `cordis@4.0.0-rc.12`，禁用 npm 安装脚本；用项目现有 esbuild 0.25.12，以 `platform: browser`、`target: chrome120`、IIFE、压缩模式打包。入口只导入 `Context` 并暴露给实验环境，没有安装 loader/HMR。

| 检查 | 观察结果 |
| --- | --- |
| 核心浏览器目标打包 | 成功；无外部导入；29,535 字节，gzip 10,320 字节 |
| 无 `process` / `require` 的 Node VM 上下文执行 | 成功建立 `Context` |
| 100 次挂载、事件触发、卸载 | 100 次预期回调；100 次清理；最终登记资源数与 registry 大小均为 0；卸载后事件不再命中旧监听 |
| 两个订阅者依次监听同一事件，第一个同步抛错，使用 `Context.emit()` | 异常传到调用方，第二个监听器未运行 |

这表明核心可以作为浏览器打包候选，且本次登记资源的卸载符合预期；也证明不能直接把 `ctx.emit()` 当作故障隔离总线。`parallel()` 在源码中使用 `Promise.allSettled()`，但并不自动给永不结束的任务增加超时或容量限制。

上述体积是本实验入口的产物大小，不是接入应用后的体积增量。实验没有覆盖真实 Chrome 扩展 CSP、BFCache、Service Worker 回收、内存长期增长或真实直播；不能据此认定已完成浏览器兼容与稳定性验收。

## 建议的工具宿主边界

工具宿主先运行在现有隔离世界应用层。直播协议桥、后台存储入口、礼物账本与发送结果跟踪继续作为稳定基础设施；每个执行环境独立初始化，不能把一个 Cordis Context 直接共享到 MAIN 世界或后台。

建议的新增目录是实施草案，当前尚不存在：

```text
src/tools/
  registry.js             包内工具注册与元数据校验
  runtime.js              挂载、卸载、故障状态及资源作用域
  contracts.js            工具接口版本与上下文约定
  auto-like/
    index.js              包装现有 AutoLike 的生命周期
    view.js               工具视图与交互
```

插件描述包含 `id`、工具版本、宿主 API 兼容范围、状态 schema 版本、所需能力和视图入口。统一 `mount(ctx, config)` 并返回可等待的卸载函数；单次任务完成与插件停用分开，不能把“停止点赞”误实现为卸载整个工具页面。

| 宿主提供的能力 | 接口原则 |
| --- | --- |
| 直播事件订阅 | 按类型订阅，每个工具独立有界队列；默认是可丢弃的辅助事件消费，不挂在核心日志确认路径上 |
| 共享直播上下文 | 返回受限副本或真正只读的结构，沿用来源、时间、缺失和估算标记；不交出可写 Engine |
| 弹幕发送 | 进入现有发送调度、限流、检查点和结果确认路径，工具不能私建发送队列绕过这些约束 |
| 点赞、管理等平台操作 | 由能力网关验证工具、房间、实际账号权限、锁、会话代次与预算，保留现有结果未知语义 |
| 定时器、事件监听、Observer、请求 | 通过资源作用域登记，卸载时清理；用 AbortSignal 协作取消并拒绝过时代次的结果 |
| 工具状态存储 | 按工具 ID、房间和 schema 版本隔离；迁移失败只停用相关工具，不覆盖原状态 |
| UI 注册 | 导航、工具页面和操作处理由同一份工具注册信息派生，避免继续增加 `auto-like` 特判 |
| 运行诊断 | 显示工具版本、状态、最后错误、队列水位和任务耗时，允许单独停用或重建 |

同一执行环境内的能力接口是工程约束，不是对恶意代码的安全沙箱。因此第一阶段只接入随扩展包发布、受维护的工具。未来若开放第三方代码，需要重新设计隔离与分发，而不是仅增加插件安装按钮。

如果采用 Cordis，应把 `Context`、Fiber 与依赖声明封装在 `runtime.js` 适配层内。业务插件依赖项目自己的工具接口，避免把尚未稳定的框架 API 扩散到所有业务模块。只需要简单依赖检查时先做启动校验；不要逐步自建完整的响应式依赖框架。

## 为可恢复运行补上的约束

### 插件事件不能改变现有确认语义

目前事件日志在核心检查点成功后确认，已经确认的记录并不是可供未来插件任意回放的历史事件仓库。接入工具时必须选择消费等级：

- 辅助工具使用独立内存队列；慢消费、失败或容量耗尽只降级该工具，明确显示缺口，不拖慢礼物与核心处理。
- 需要可靠处理的工具，由宿主在核心日志确认前可靠写入专用 outbox，或扩展为有独立消费游标的保留日志；按稳定事件 ID 去重。无法保证写入时显式降级，不能声称已经交付。
- outbox 同样需要容量、水位、重试与确认边界；不能把全部插件状态简单塞进主快照，也不能因为插件回调已返回就确认真实平台操作成功。

### 独立启停与受控替换

包内工具实例重建应串行进行：校验新配置／兼容性 → 暂停向旧实例投递任务 → 撤销旧代次继续提交操作的资格 → 等待在途请求结算或记录未知 → 保存工具状态 → 卸载旧实例 → 挂载新实例 → 就绪后授予新代次操作资格。

新实例启动失败时，清理其登记资源，使用仍兼容的状态恢复旧实例，或将工具保持停用。不能让旧实例和新实例同时持有可发送资格；恢复旧代码和状态也不能撤销已提交的点赞或弹幕。

只有扩展包中已经存在的代码才能通过这条路径重建实例。安装新扩展包时，还要处理 `page.js`、`content.js` 和后台的新旧协议共存：增加协议版本／构建标识握手、支持明确的兼容范围；不兼容时停止相关操作并引导刷新。不能假设整包更新同时替换所有打开页面的脚本。

### 故障隔离的真实边界

宿主应逐个捕获工具回调的同步异常与异步拒绝，限制队列、并发和执行预算，连续失败时停用单个工具。Promise 超时只代表停止等待；插件必须配合取消和代次检查，不能依靠 `Promise.race()` 阻止晚到回调继续发送。

同一线程中的死循环、长时间同步计算和内存耗尽仍能影响直播页。后续音视频、识别或大批量统计应放入可终止的 Worker、具备实际 API/生命周期条件的扩展文档，或云端服务；DOM 和平台操作留在宿主。具体容器需按任务权限和 MV3 能力验证，不能默认内容脚本能直接创建任意 Worker。

后台 Service Worker 的内存注册表可以重建，持久状态必须从存储恢复；Chrome 事件监听应在顶层同步登记，再把事件交给已初始化的宿主。不能假设退出时一定执行 `dispose()`，也不能靠插件计时器保证后台常驻。[Service Worker 生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)、[后台导入方式及动态 import 限制](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/basics)。

## 方案比较

| 方案 | 当前收益 | 主要成本 | 决策 |
| --- | --- | --- | --- |
| 继续直接在 app/panel 中接线 | 新增一个小功能最快 | 生命周期、菜单和错误处理持续分散 | 不作为后续工具开发规范 |
| 小范围工具宿主与稳定接口 | 满足包内工具注册、独立启停和回收 | 维护有限生命周期和业务能力适配 | 当前优先 |
| Cordis 核心 + 项目适配层 | 进一步复用依赖注入、effect 与服务生命周期 | RC API、构建接入、跨环境及业务持久化适配 | 候选，待真实工具试点比较 |
| Cordis loader/HMR/市场整套接入 | 在 Node 插件平台有更完整的工具链 | Node 依赖与当前扩展约束不匹配，不能提供整包发布替代品 | 当前不引入 |
| 微前端框架或模块联邦 | 适合独立团队、独立部署的页面应用 | 对当前工具规模增加构建与运行复杂度，仍需处理远程代码边界 | 当前缺少对应需求 |

Cordis 对未来 Node 云端工具宿主可能更合适；但服务端的高可用仍需要进程监督、持久队列、健康检查和部署回滚，HMR 不能替代这些机制。这是架构判断，未在本仓库中验证云端实现。

## 建议实施顺序与验收

1. 先定义工具接口、资源作用域和 UI 注册点，选定状态与操作网关的归属。保留当前核心事件、账本和发送链路。
2. 包装现有自动点赞作为首个插件，复用 `AutoLike`、房间锁和请求桥；检查停止、在途结果、切房、断线、BFCache 与上下文失效行为。
3. 用下一个真实工具验证接口，比较轻量宿主与仅嵌入 Cordis 核心的实现；若采用 Cordis，固定精确版本并通过隔离适配层接入，不直接跟随 `latest`。
4. 引入需要可靠事件处理的工具时，再实现独立 outbox／消费游标；引入重计算时，再落实可终止的执行容器。
5. 完善正式更新：受限配置更新可校验并回退，代码随包发布，直播期间优先选择安全更新时机；开发更新继续明确提示刷新存在采集窗口。

运行时实施后的必要验收包括：反复启停后监听与资源不累积；工具 A 抛错或挂起时工具 B 和核心继续处理；停用与切房后的旧回调不能提交新操作；在途平台结果未知时不自动重发；辅助工具拥塞不阻塞核心；可靠工具在崩溃回放后能去重；状态迁移失败不破坏旧数据；新旧脚本协议不兼容时可明确降级；真实 Chrome 中覆盖后台回收与页面恢复。

本轮只验证了前述独立实验，并检查了当前源码和官方资料；以上产品验收尚未执行。下一步最有价值的交付是“自动点赞插件化试点”，其结果再决定是否将 Cordis 核心纳入正式依赖。
