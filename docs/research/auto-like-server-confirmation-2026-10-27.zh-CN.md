## 修复行为

旧实现把 `status_code=0` 直接计入进度，会在服务器未提供实际点赞回执时显示成功。现在每批提交前订阅网页已解码的 `LikeMessage`，HTTP 成功且收到当前账号对应数量的真实广播才累计“服务器已确认”。

- 其他观众的总数增长、空回包、本地 mock 消息均不计入确认。
- 按消息 ID 去重，支持本账号回执拆分成多条；若消息带房间 ID，还须匹配当前房间。
- 每批确认窗口从提交前开始，最多 10 秒；超时停止，不重试、不切换接口补发。
- HTTP 拒绝或异常及时移除监听；切房、换账号或消息服务替换使当前确认失效。
- 重复桥消息复用同一 Promise；停止后仍等待已发批次结果，不继续调度。

IM 没有本次 HTTP 请求的关联 ID，因此同账号同时手动点赞会影响归属。界面提示确认期间不要手动点赞。未收到广播表示“无法确认”，不能断言服务端最终没有计入；保守停止会降低吞吐，也可能在平台不向当前页广播本人点赞时停止。

本次修复解决虚报成功和继续发送的问题；本账号在该直播间实际入账的成功证据仍未取得。不能把这次改动描述为已经恢复平台端入账，也不通过修改本地点赞总数来制造成功。

## 2026-10-28：修正无本人广播时的误停

报错“请求已返回，但未收到本账号的服务器点赞回执”由助手额外添加的确认条件触发。已有证据只支持“请求成功、未观察到本人广播”，不能据此推导“点赞失败”；原生网页也没有以本人广播作为请求成功的条件。

现在继续使用网页签名客户端提交相同的 `POST /webcast/room/like/`、空 JSON body 和当前房间的 `room_id/count`，严格以数值 `status_code === 0` 判定平台接受，随后按设定间隔串行执行下一批。删除本人 IM 订阅和 10 秒确认等待，不再因消息服务缺失、替换或未广播本人点赞而停止。进度统一显示“平台已接受”，并说明最终展示以直播间为准；没有修改本地点赞总数，也没有将空回包表述为实际入账证明。

每批仍只提交一次。重复桥消息复用原结果；停止会阻止后续批次，已在途请求等待结算。平台拒绝、异常或无效响应停止且不重试；提交前后核对房间、账号及点赞权限。桥响应超时调整为 10 秒，覆盖接口的 8 秒超时。

回归测试覆盖原生空成功回包、无本人广播、无 IM 服务或订阅故障、在途切房/换账号/权限变化、停止后的迟到成功、畸形状态码，以及构建后的 MAIN 与隔离桥连续提交 3/3/1 且重复批次不重发。
