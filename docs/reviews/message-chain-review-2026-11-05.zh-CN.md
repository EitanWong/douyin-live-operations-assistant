| P1 | 解码缓存满载时再次解码原始帧，绕过第一次跨传输去重，重复交付同一事件 | 保留首次去重的事件位置决策；真实 protobuf 回归从 `[101,101,102,103]` 恢复为 `[101,102,103]`，不二次更新去重表 |
| P1 | XHR 长轮询中止后复用，旧 load 监听未清理；下一次请求被重复采集，甚至非 IM 响应也被误读 | 每个 XHR 只保留当前请求的观察器，在成功 open、load、loadend、发送异常处回收；同路径与非 IM 路径复用红测转绿 |

| P1 | DOM 备用采集遇慢订阅时等待数组无界，持续直播可能耗尽内存 | 等待与正在处理的数据共享 4096 条 / 8MiB 序列化预算；拒收明确记入 DOM 缺口。4096 条阻塞后顺序交付、额外 10 条明确报告；超大消息拒绝 |

| P2 | 连续保存时旧请求失败，会覆盖较新的乐观值；连续失败可能回滚到另一个未成功值；外部存储更新也可能被覆盖 | StorageMirror 分离确认值与最新操作，仍由单写者串行保存；旧失败不动新操作，迟到响应不覆盖已观察通知；三项集成红测和删除/迟到成功专项通过 |

## 性能证据

执行 `node scripts/benchmark-ingestion.mjs` 可复测。环境为 macOS arm64 / Node v26.12.1；固定 2 万条未过期记录，对 1000 次跨传输查询执行预热与 11 次采样，交替顺序重复三轮。旧实现每轮中位数 58.46–63.27ms，当前实现 0.064–0.108ms。原始数据见 [ingestion-benchmark-2026-11-05.json](ingestion-benchmark-2026-11-05.json)。

此结果只说明指定去重热点的 CPU 成本，不能换算成整个扩展、网络发送或实播吞吐的加速倍数。普通回归不以机器相关耗时为门槛。队列按条数和序列化大小限制；该大小不是 JavaScript 堆、Chrome RSS 或扩展总内存上限。

## 尚需优化或测量的边界

| 后续重点 | 当前证据与限制 | 建议验收方式 |
| --- | --- | --- |
| 真实端到端延迟 | content 无积压时 200ms 轮询，前台新增消息可能等待约 0–200ms，再叠加 Chrome 调用与处理；DOM 首批有 50ms 合并。后台节流可能更长 | 实播分别记录接收、解码、跨世界交接、入队、持久化、发送与回显的 p50/p95/p99；决定是否采用受限唤醒信号或自适应轮询，兼顾 CPU/电量 |
| 存储与预测阻塞 | app 按事件等待预测写入，客户端和后台预测服务均串行；大报告/导入与其他房间写入会共用后台队列 | 使用实际档案体量测报告和事件写入耗时；在保持事件幂等、事务与检查点语义的前提下评估分房调度或批量写入 |
| 极大帧主线程占用 | 原始帧/解码缓存有预算，但单次同步解析与消费者执行不能被 8ms 合作让出抢占 | 用高分位真实帧录制回放做长任务分析；必要时拆解析或迁至 Worker，先确认转移/复制成本 |
| 崩溃与刷新恢复 | 桥接 ack 只表示进入 content 有界队列，不是落盘确认；浏览器崩溃、扩展上下文销毁、页面离开会丢未持久化数据 | 故障注入与冷重启验证已落盘日志可回放；若要求更强保证，单独设计持久接收确认，不能宣称本次已做到端到端 exactly-once |
| DOM 页面生命周期 | stopDOM 会取消尚未交付的 DOM 快照；DOM 仅能看到网页实际呈现内容，虚拟列表未呈现的消息无法抓取 | 实播验证挂起/恢复及虚拟节点复用，优先以原生协议采集；不能以“未发现缺口”宣称完整采集 |
| 长期内存与平台变化 | 各层均有独立预算，并非一个总进程预算；协议/DOM 变化、浏览器休眠、弱网与 MV3 重启仍依赖真实环境 | 至少覆盖高峰/静默、多标签、断网重连、后台节流、24–72 小时运行；观察 RSS、堆快照、队列水位、缺口与未知 method，不用短测试替代 |

本轮没有向真实直播间发送测试消息，没有宣称达到性能极限或完成全天稳定性验收。crapper、dryer、mutator 在命令、项目脚本及启用工具中均不可用，未执行；普通回归不代表这三项通过。
